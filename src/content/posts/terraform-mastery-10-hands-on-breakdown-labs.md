## Lab 01: Core workflow and provider trace

### Purpose

Observe initialization, validation, planning, apply, state inspection, and destroy
with local-only providers.

### Learning outcomes

- classify artifacts created by `terraform init`;
- distinguish validation and planning from apply effects;
- observe provider lifecycle trace events without treating log wording as an API;
- inspect state through supported Terraform commands;
- verify cleanup of the managed local file.

### Cost and safety boundary

This lab creates one JSON file, random state, and Terraform working artifacts on
the local machine. It calls the Terraform Registry during first initialization but
uses no cloud account and creates no paid resources. Debug logs and saved plans can
contain sensitive data; do not publish them.

### Prerequisites

- Terraform compatible with `required_version`;
- network access for the first provider installation;
- write permission in this directory.

### Predict before running

Draw the sequence `init → validate → plan → apply → inspect → destroy`. Predict
which step first creates `server_manifest.json` and which files should remain after
destroy.

### Procedure

```bash
terraform init
terraform validate
terraform plan -out=lab01.tfplan
terraform show lab01.tfplan
TF_LOG=DEBUG TF_LOG_PATH=lab01-debug.log terraform apply lab01.tfplan
terraform state list
terraform show -json
terraform destroy
```

Delete the sensitive saved plan and debug log after inspection.

### Expected evidence

- `.terraform/` contains installed provider packages and working metadata;
- `.terraform.lock.hcl` records provider selections and checksums;
- the plan proposes the local file but does not create it;
- apply creates `server_manifest.json` and state binds its Terraform address;
- destroy removes the managed file.

### Failure experiment

Add an unsupported argument to `local_file.server_manifest`. Predict and observe
the validation diagnostic, then restore the configuration.

### Cleanup

```bash
terraform destroy -auto-approve
rm -f lab01.tfplan lab01-debug.log
```

The explicit `rm` targets only disposable artifacts named by this lab.

### Automated verification

```bash
./verify.sh
```

The verifier initializes, validates, applies, asserts the file and output, destroys,
and asserts removal.

## Lab 02: Module contracts and operation graph

### Purpose

Observe module address namespaces, reference-driven dependencies, graph output,
and native Terraform tests in a local-only topology.

### Learning outcomes

- trace inputs and outputs across child-module boundaries;
- predict graph edges from references rather than file order;
- inspect module-qualified state addresses;
- run `.tftest.hcl` assertions;
- distinguish a DOT graph from a stable internal execution API.

### Cost and safety boundary

This lab creates random values and local files only. Provider installation may use
the network. Graphviz is optional for manual study and required by `verify.sh` to
render the PNG; no cloud credentials or paid resources are used.

### Prerequisites

- Terraform and the `dot` command from Graphviz;
- network access for first initialization;
- write permission in this directory.

### Predict before running

Draw the network module, compute module, and independent cluster-name branch.
Predict which compute expressions create edges to network outputs.

### Procedure

```bash
terraform init
terraform validate
terraform test
terraform graph > dag_graph.dot
dot -Tpng dag_graph.dot -o dag_graph.png
terraform apply
terraform state list
terraform destroy
```

### Expected evidence

- native tests pass their plan and apply assertions;
- graph output contains module relationships and internal nodes;
- state addresses include `module.network` and `module.compute` namespaces;
- the independent random-pet branch does not require network output values.

### Failure experiment

Temporarily set `node_count = 0`. Predict which validation fails and whether any
resource operation begins. Restore the value afterward.

### Cleanup

```bash
terraform destroy -auto-approve
rm -f dag_graph.dot dag_graph.png
```

## Lab 03: Local state-lock contention

### Purpose

Observe two Terraform processes competing for one local-backend state lock and
separate that evidence from remote-backend locking architecture.

### Learning outcomes

- identify the lock holder and rejected contender;
- explain why state locking serializes writers;
- use `-lock-timeout` deliberately;
- distinguish a local process lock from distributed backend locking;
- state the evidence required before force-unlock.

### Cost and safety boundary

This lab uses local providers, a four-second delay, local state, and two log files.
It creates no cloud resources. It must not be used to test `force-unlock`, and it
does not prove S3, HCP Terraform, GCS, or another backend's locking implementation.

### Prerequisites

- Terraform and a POSIX-compatible shell;
- network access for first provider installation;
- no other Terraform process using this lab directory.

### Predict before running

Predict which process exits non-zero, what lock evidence it reports, and whether
the successful process leaves a valid state binding.

### Procedure

```bash
terraform init
./test_race_condition.sh
terraform state list
```

### Expected evidence

- process 1 holds the lock during a forced slow replacement or creation;
- process 2 exits non-zero with `Error acquiring the state lock`;
- only the successful writer updates state;
- a later operation succeeds after normal lock release.

### Failure experiment

Change the second process to use a short positive `-lock-timeout`. Predict whether
it still fails or waits long enough to succeed. Restore the zero-timeout test.

### Cleanup

```bash
terraform destroy -auto-approve
rm -f proc1.log proc2.log lock_test_output.json
```

### Automated verification

```bash
./verify.sh
```

- execute a configuration-driven import in isolated state;
- generate a fresh plan after every state-changing experiment.

### Cost and safety boundary

resource in disposable directories. No cloud account or paid resource is used.

- network access for first installation of local/random providers;
- write permission for this directory and the system temporary directory.

## Lab 05: Multi-stack boundary simulation

### Purpose

Model four independently initialized Terraform roots with explicit published data
contracts and reverse-order cleanup.

### Learning outcomes

- distinguish a child module from a separate root/state boundary;
- order bootstrap, networking, database, and compute roots explicitly;
- inspect values published between stacks;
- test input validation and lifecycle preconditions;
- evaluate the limits of file-based integration.

### Cost and safety boundary

This is a local simulation, not a production cloud architecture. It creates random
identifiers, JSON contract files, four local states, and one application manifest.
It uses no cloud credentials or paid resources. The shared directory is a teaching
substitute, not a recommended secret store or cross-stack production mechanism.

### Prerequisites

- Terraform and a POSIX-compatible shell;
- network access for first provider installation;
- write access across the lab directory.

### Predict before running

Draw the four roots and the exact JSON files passed between them. Predict which
root fails if `network.json` or `database.json` is absent.

### Procedure

```bash
./verify_all.sh
```

The master verifier runs Labs 01–04, then initializes and applies the four Lab 05
roots in order and destroys them in reverse order.

### Expected evidence

- every root has its own state and provider installation;
- `bootstrap.json`, `network.json`, and `database.json` form explicit contracts;
- compute reads network and database outputs without direct state coupling;
- validation rejects an invalid database class;
- cleanup removes managed files and disposable shared contracts.

### Failure experiment

In a disposable copy, run compute before database and classify the missing-contract
diagnostic. Then restore the correct pipeline order.

### Cleanup

Destroy roots in reverse dependency order: compute, database, networking,
bootstrap. Remove only the three named shared JSON files and the empty directory.
`verify_all.sh` performs this sequence automatically, including on interruption.
